# 実物を確かめたうえでの修正要件

利用者が画面の実物を確かめて挙げた指摘を、修正要件として記録する。ここではまだ実装しない。指摘がそろってから、タスクに分けてまとめて直す。

- 番号は、利用者が挙げた順
- 「指摘」は利用者の言葉の要約。「補足」は指示役が調べたことや、今の作り。「決めること」は、直す前に決める点

## 1. 日付を選ぶカレンダーに、祝日を色で出す(11/3)

- **指摘**:日付を選ぶカレンダーに、祝日を反映した色付けをするべき
- **補足**:
  - 今は、ブラウザ標準の日付の欄(`input type=date`)を使っている。標準の欄は、日ごとに色を変えられない。カレンダーの部品(shadcn/ui の Calendar など)に替える必要がある
  - 該当する欄は、方針の期間の開始日・終了日(`PolicyStep`)と、到達圏を比べる日(`DateBandStep`)
  - 祝日は、内閣府の祝日一覧(`store/holidays.ts`)から取れる
- **決めること**:
  - 色の付け方。日本のカレンダーの慣例(日曜・祝日は赤、土曜は青)にするか
  - 祝日の名前を出すか(マウスを載せたときなど)
  - 入力の GTFS の有効期間の外の日を、選べないようにするか、薄く出すか
  - その日にどのダイヤ(平日・土曜・日祝)が走るかも、カレンダーに出すか

## 7. 「日付と時間帯」の設定のうち、地図の表示にしか効かないものは地図の側に移す(11/3)

- **指摘**:手順3(日付と時間帯)では、日付・時間帯の幅・時間帯を操作できる。これが地図の表示にしか効かないなら、この設定は地図の側に移すべき
- **補足**(11/3 に指示役が確かめた、今の作りでの効き方):
  - **表示する時間帯**(どの時間帯を見るか):地図の塗り分けと、手順4の表で強調する行に効く。計算は変えない。地図の側に移せる
  - **日付**と**時間帯の幅**(1時間ごと・3時間ごと):到達圏の計算そのものを変える。効くのは、地図、手順4の表(全時間帯の外れるセルの数と割合)、手順5の足し戻しの手がかり(「外れたセルが戻る」「停留所で唯一の便」は、比べる日の値)、AI の影響の要約(`summarize_impact`)。地図だけの設定ではない
  - 方針を承認した後は、外れたセルが最も多い時間帯を自動で選び直している(「決めておくべき事項」の 11/3 の決定 12)
- **決めること**:
  - 表示する時間帯を、地図の上の操作(時間帯の切り替え)に移すか
  - 日付と時間帯の幅を、地図の側に移すか、手順に残すか。地図の側に移すなら、表と手がかりも同じ設定で計算し直されることが分かるようにする(例:地図の上の設定を変えると、手順の表も変わる)。3(ステッパー)と4(地図を出さない手順)と合わせて決める
  - 手順3を残すか、ほかの手順にまとめるか

## 8. 処理中のボタンと、GTFS の読み込みの欄(11/3 夜)

### 8.1 処理中のボタンは、文字をスピナーに置き換えて無効にする

- **指摘**:ボタンを押して何かの処理が走っている間(読み込み中を含む)は、ボタンの元の文字を読み込み中のスピナーに置き換えて、ボタンを無効にする。今の「サンプルを読み込む(道北バス)」は、処理中にボタンの下へ「読み込み中」の文字を出すが、これは表示の要素を無駄に増やすだけ
- **補足**:
  - 今の読み込みの手順(`web/src/components/steps/LoadStep.tsx`)は、処理中に2つのボタン(ファイルを選択・サンプルを読み込む)を `disabled` にし、下に「読み込み中…」の行(160 行目)を足している
  - 同じように、処理中を別の文で知らせているところがほかにもある(`git grep` で「読み込み中」「計算しています」「送っています」「作っています」などが当たる部品:DataSources、ChatPanel、ChangeOrder、NoticeDraft、ReachStep、PeriodFields)。ボタンに結び付いた処理なら、同じ規則に合わせる
- **決めること**:
  - ボタンの部品(`components/ui/button.tsx`)に「処理中」の状態を持たせ、どのボタンも同じ見た目にする(スピナーだけにするか、スピナーと短い文にするか。ボタンの幅が変わらないようにする)
  - スピナーにしても、画面読み上げに処理中であることが伝わるようにする(`aria-busy`、読み上げ用の文)
  - ボタンに結び付かない長い処理(到達圏の計算、AI の返答待ち、前提情報の調査の進み具合)は、この規則の外にして、今の進み具合の表示を残すか

### 8.2 読み込んだ GTFS のファイルを、Attachment の部品で見せる

- **指摘**:GTFS のファイルを選んだとき、またはサンプルから読み込んだとき、「ファイルを選択」の欄に shadcn の Attachment の部品で、ファイル名・状態・ファイルの大きさなどを出す
- **補足**:
  - 今は、標準のファイルの欄と、読み込んだ後のファイルの一覧(表ごとの行数)を出している
  - shadcn/ui の Attachment の部品が、レジストリのどこにあるか(公式の部品か、ほかのレジストリか)は、直すときに shadcn の MCP サーバーで確かめる
  - サンプルを読み込んだときも同じ部品で、ファイル名(例 `dohoku_bus_減便前.zip`)・大きさ・状態(読み込み中・読み込み済み・失敗)を出す
- **決めること**:
  - 部品に出す項目(ファイル名、大きさ、状態、読み込んだ日時、サンプルかどうか、取り除くボタン)
  - 取り除くボタンを付けるなら、編集の履歴が消えることの確かめ(今の「読み込み直すと編集は消える」の扱い)

### 8.3 「ファイルを選択」と「サンプルを読み込む」の間に「または」の区切り

- **指摘**:「ファイルを選択」と「サンプルを読み込む」のボタンの間に、横棒と、その中央に「または」を出し、2つから1つを選ぶ形だと分かるデザインにする

## 13. 画面の文の読みにくさと、一般的でない語を、アプリ全体で直して統一する(11/3 夜)

- **指摘**:アプリの文は認知の負荷が高い。一般的な表現でない語もある(例「消える n 便・入る n 便・残る n 便」、「下書き d1」の「d1」、「足し戻し」)。agy(Antigravity CLI)の Gemini 3.8 Flash か Gemini 4 Argon に、yomiyasu のスキルを使って改善を頼み、アプリ全体で、言い回しと語がより自然で、かつ統一されるように直す
- **補足**:
  - 道具はこの Mac にある:`agy` 1.4.12(モデル `gemini-4-argon-high`・`gemini-3.8-flash-high` など)、yomiyasu 2.5.0(agy のプラグイン。`~/.gemini/config/plugins/yomiyasu`)
  - 語の広がり(11/3 に数えた):「足し戻」は `web/src` に 253 か所。「下書き d1」の形の ID の表示は 28 か所。「消える・入る・残る」は 23 ファイル。AI の定義(`agents/coordinator.md` 17 か所、`claude_tools.json` 8 か所)にも同じ語がある。AI が利用者に話す語と、画面の語をそろえる必要がある
  - 「足し戻し」は、Notion の決定事項・CLAUDE.md・取り決めの文書でも使っている業務の語。画面の語を変えるなら、文書をどこまで合わせるか(画面と AI だけにするか)を決める
  - AI の定義(システムプロンプト・ツールの説明)を変えると、`ant apply` で調整役の版が上がる(利用者の承認が要る)。[画面の操作] の行の文(「下書き d3 を利用者が承認しました」など)も、AI に伝わる語として合わせる
  - テストは画面の文を多く確かめているので、文を変えるとテストも直す
- **進め方**(指示役の案):
  1. 画面の文と語を集める(部品・文言の定数・AI に送る行・AI の定義)
  2. agy(Gemini)に yomiyasu で頼み、(a) 語の表(今の語 → 直した語、使い分けの規則)と、(b) 画面の種類ごとの書き方の決まり(ボタン・見出し・説明・注意・エラー)を作る。読者は運行管理者と GTFS 担当者(バスの業務には詳しいが、Dispatcher の造語は知らない)
  3. 語の表と決まりを、指示役が確かめる(業務の正しい語、GTFS・法令の語、数はコードが出す方針を崩さないか)
  4. 表と決まりに従って、画面の文を直す(Claude の担当)。直した文の一部を、もう一度 agy に見せて確かめる
- **決めること**:語の表の採否(とくに「足し戻し」の言い換え)、下書きの ID を画面に出すか(出さずに「AI が作った案」などと呼ぶか)、文書(Notion・CLAUDE.md・取り決め)をどこまで合わせるか、AI の定義を変えて `ant apply` するか
